## 任务一句话

**直接在当前 Glyph Rumble 3D 代码仓库中，将本包所有文化、成语、影视类型、网络、单字、词语以及篮球搭档点子接入游戏；保持 Arena 已有角色和必杀技；保持足球 4v4、篮球 2v2；保留旧功能，去重并复用共用行为。完成后提交代码、测试和技能图鉴。**

## 用户已经决定的产品设定，禁止擅自改动

1. 现有 Vite/Three.js 浏览器项目及 Arena 不改玩法，角色的 3D 字形、原始属性、人格、技能名、旧必杀技、外观依旧是**唯一共享角色身份**。
2. 足球严格 **4v4**：一键组队模式把四个 Unicode 字素簇拆成四名球员，例如 `少林足球` → 少/林/足/球；自由组队模式每格是一个完整角色，例如 `妈妈 / 爸爸 / 宝宝 / 奶奶`。球队名称本身**不是第五名球员**。可输入未登记的任何四个有效字。
3. 篮球严格 **2v2**：一键搭档模式把两个 Unicode 字素簇拆成两名球员，例如 `冰火` → 冰/火；自由模式可用 `妈妈 / 404` 这种完整角色，两者不能混淆。可输入未登记任意两个字。
4. 现有足球 README 中的 12 个成语连携（龙飞凤舞、风平浪静、火上浇油、画蛇添足、一鸣惊人、虎头蛇尾、四面楚歌、天马行空、鸡飞狗跳、乱七八糟、无法无天、大吉大利）**优先保留已有实现**。目录内若再次出现同一键，视为对现有条目的补充/注释，不能覆盖已正常工作的逻辑和参数。其余旧招式、旧文化标签亦然。
5. 继续保留实际足球物理、门线判定、计分、动态门将、AI 跑位、正常传球、铲球、比赛结算与分享。篮球保持真实球权、抢断、投篮、篮筐及篮板判定。**任何文化技能不得直接写入比分或强制宣告得分**。
6. 比赛保持固定步长模拟、seeded RNG 和确定性回放。随机故障、乌龙、幽默效果必须通过种子及可验证条件决定，不准偷偷使用 `Math.random()` 破坏回放。
7. 游戏不需要在运行时请求 LLM，不强制注册，不新增昂贵后端；目标是公开发布免费网页游戏。兼容中、日、英和 Emoji/颜文字。保留 SNS 战报/挑战链接协议。

## 一次性执行方式——禁止分期式交付

- **一次读取整个任务包和现有项目，不要让用户再分批复制内容。** 自己建立内部任务清单和依赖关系，然后连续开发，直到对目录所有条目有明确处理结论。
- 不要提问「先做哪 10 个」「下一批要不要做」「等确认再继续」。开发时可以按内部技术顺序推进，但最终交付必须覆盖全表。
- 先检查旧代码，再实现新公共原语和数据表，最后批量接入条目；**不要给每个点子复制一套独立渲染器/AI**。
- 仅在出现无法由现有环境解决的硬性障碍（例如仓库不可访问）时报告；其他设计细节自行采取保守、可测、好玩的实现。
- 不允许将尚未实现的条目冒充完成。某条涉及真正的新运动动作时，就实现动作及物理逻辑；做不到则记录具体原因、测试状态和文件位置，**继续处理剩余条目**。
- 这是完整开发任务；不要只输出策划案、静态 JSON、README、菜单或屏幕上弹出名字却没有行为的伪技能。

## 技能层级及优先级

**L1｜角色字形/语义层：** `03_单字与完整词语角色.tsv` 每条是角色本身已有或者待新增的特性。先检查项目原词库；如果角色已存在且技能等效，复用并标记 `existing`。其他角色实现对应动作、短时状态和三种模式映射。不要因为 `妈妈` 有两个汉字，就把她在自由组队模式拆为两名球员。

**L2｜体育队伍层：** `01_足球四字文化连携.tsv` 的每个键是一个**四人足球队**，`02_篮球双字文化搭档.tsv` 的每个键是一个**两人篮球队**。技能只有当**完整组合匹配**、本局触发条件成立且冷却允许时才发动；不是只要场内出现其中一字就触发。英文字母组成的四字符组合也必须有效（HERO、FOMO 等）；日文四字保持日文名称。

**L3｜文化对阵层：** `04_特殊对阵与文化彩蛋.tsv` 是**两队对阵关系**，应在两队均符合规则时生效，且允许调换蓝/红队顺序。含解说、镜头、小范围真实状态互动；不要完全覆盖双方单独的球队必杀技。跨队技能的同时触发优先级和冷却必须确定。

**L4｜通用兜底：** 没有明确条目的新输入继续使用已有字形属性、通用必杀技和普通 AI，绝不可因为词典里没有就无法玩。

触发优先级建议：已有玩家选择的完整角色技能 > 精确球队组合匹配 > 该场特定对阵彩蛋 > 标签可复用表现 > 通用字形兜底。`已实现` 优先复用而不是覆盖。不要从电影标题或人名自动推导任何现实人物的身体信息。

## 建议共享行为原语（必须能对球和角色产生真实结果）

通过已有代码辨识可复用内容，按需新增少量共用动作，每行可组合 1～3 个行为原语，而不是制造大量新 Shader。以下为能力集，不要求照名字建文件：

- 足球：`fakeShot` 假射、`passChain` 连传、`redirectPass` 折线传球、`curveKick` 曲线射、`lobKick` 高吊球、`boardBounce` 围板反弹、`chargedKick` 蓄力重射、`throughBall` 穿透性直塞、`sprintLane` 边线冲刺、`roleSwap` 换位、`markConfusion` 错误盯防、`intercept` 拦截、`block` 临时阻挡、`keeperRush` 临时门将扑救、`decoyVisual` 无碰撞假影、`selfTrip` 自己绊倒、`reboundRisk` 失误反弹、`allyRally` 短暂队友提振。
- 篮球：`screen` 挡拆、`pickAndRoll` 挡拆顺下、`giveAndGo` 传切、`crossover` 变向、`pumpFake` 假投、`alleyOop` 空中接力、`highArcShot` 高抛、`bankShot` 打板、`stealWindow` 抢断窗口、`reboundRead` 判断篮板、`contestShot` 干扰投篮、`blockShot` 盖帽、`passCurve` 曲线传球、`fastBreak` 快攻、`backdoorCut` 反跑、`miscommunication` 配合失败。
- 三模式共用：`pushback`、`temporarySlow`、`shortStun`、`visualDecoy`、`projectedArea`、`collisionProp`、`temporaryScale`、`animationPose`、`audioCue`、`cameraBeat`、`comedicSelfPenalty`、`eventCommentary`。

为每个原语定义明确的状态变化、起手条件、时间窗口、强度上限、碰撞层、播报事件和失败分支。**至少一项玩法效果必须能被自动化测试观测**，并且让普通观众从画面上理解它为什么发生。

## 文档每行如何落地

每条记录都至少落成可执行的结构化数据：

- `id` / `canonicalInput` / `aliases` / `mode` / `level`
- `localeLabels`（中文、日文、英文描述；名称可保留原语言）
- `cultureTags`（movie-inspired、anime-inspired、folklore、history、idiom、society、tech、internet、everyday 等）
- `triggerCondition`（明确、自动、可重复的球场条件）
- `cooldownSec`、`maxUses`、`priority`、`durationSec`
- `actions`（共用原语 + 目标与参数；禁止仅是视觉特效）
- `selfRisk` / `failureBranch`（可能踢偏、撞板、空门、配合失败等，必须是合理物理事件）
- `visualCue`、`audioCue`、`commentaryIds`
- `implementationStatus`（`existing`、`implemented`、`blocked`），不能默认全部标 done
- `testId` 或 `verificationCase`。

**禁止**仅把所有记录映射到同一项 `powerShot` 加不同颜色。重复的文化意象可以共享底层动作，但场上行为至少通过策略选择、目标、队形、时间条件、负面反作用或碰撞事件形成差异。

## 设计与平衡

- 不能直接凭技能发奖励进球、凭空改变历史比分或把对手永久控制。唯一足球物理对象始终只有一个实体足球；假球只能为视觉诱导，不得生成第二个能入球门的实体。篮球同理只有一个计分用篮球。
- 文化大招存在前摇、状态条件、13～18 秒左右冷却（可按旧系统实际参数适配）、每场次数上限及至少一种反制途径。长时间控制、强制位移有明确上限。已有 12 个旧连携数值不要被新的默认值冲掉。
- 技能应允许搞笑失败：踢到门柱、错把队友当敌人、盯错球、冲过底线、集体庆祝漏防。失败是模拟里的后果而不是固定播放的假片段。
- 显示队伍与技能的文化来源，但**准确区分：影视/动画标题不是成语、历史人物不是电影作品、现代网络用语不是古典典故。** 不要把四字英语强行解释为成语。
- 避免既有 IP 的角色造型、原声、截图、影片镜头、原作招式名称、标志性构图或声线复刻。引用玩家输入中的作品文字可以作为识别入口，但官方展示使用原创字形与通用、类型化的热血或功夫表现，避免让玩家误以为与版权方有合作。
- 语言安全：网络用语只做表演而非生成针对现实个人的公开辱骂。公开分享输入需适当编码、转义、限制长度和处理举报。测试文字显示不缺字。

## 数据融合、旧系统与目录

建议结构在 `shared/src/sports/combos.ts` 及现有 `shared/src/sports/skills.ts` 附近扩展，但请先以真实仓库结构为准；不要凭文档猜源码路径。四表可以转换为 TS/JSON 数据源，只保留一个权威注册表，自动产生游戏图鉴和技能文档，禁止维护互相矛盾的多份手工列表。

- 旧技能如「少林足球」如项目已存在等效实现，应标为 `existing` 而非覆盖。
- 成语繁简体（如 龍飛鳳舞/龙飞凤舞）以及日文同形词可通过明确别名匹配，禁止过度宽泛的模糊匹配。
- 按 **Unicode grapheme cluster** 严格解析球队输入；含 emoji 组合的自由组队不能被拆坏。
- 单字、完整词语与队伍不是同一层：`爸爸` 作为篮球自由组队中一个人正常匹配角色，`爸妈` 一键搭档中则拆成爸与妈。
- 不调整当前游戏入口、Dev server 端口、分享链接与战报兼容协议；针对新内容新增可定位测试和文档页。
- 添加图鉴筛选：单字、词语、足球文化队、篮球搭档、影视文化、成语历史、日语、英文、网络科技、特殊对阵，显示实际已完成状态。
- 球场表演优先从已优化的粒子池、实例化道具和缓存字形创建，禁止每次临时创建大量 Mesh 或首次临场编译 shader；关注 4v4 八人足球、2v2 四人篮球的性能。

## 质量验证与实际交付门槛

完成后必须能独立核查：

1. 从所有四个数据表逐行验证：关键词非空、足球四字/篮球两字 Unicode 字素簇数量正确、同一模式无重复键、所引用的原语和触发器存在、注册与技能图鉴一致。
2. 逐条执行一个**确定性场景测试**：用模拟器设置能触发该技能的合理事件，检查其对应策略、移动、控球、速度、球路、拦截、计时或失败分支确实发生。不要仅验证 `lookup` 能找到一个名字。
3. 在足球 4v4 和篮球 2v2 中各进行代表性的完整自动对局：从开球/争球直到比分结算，确保角色数正确且正常走位。特殊对阵交换双方后也应匹配。
4. 保持足球单球、篮球单球、绝不强制得分、比赛确定性、种子复现、旧的 12 个成语正常、Arena 回归测试全部通过。
5. 验证开放式自由组队、成语一键拆分、中文、日文、英文四字符及 Emoji、颜文字组合；不匹配词典的队伍仍可比赛。
6. 验证不同文化技能互相叠加时不会产生永久状态、NaN、碰撞体无穷扩张、无限传球、无穷循环，且日志事件真实来源于比赛。
7. 运行生产构建、自动测试，以及可用的浏览器可视检查；无法在当前环境测试的手机型号必须明确写在人工验证表，不要假装测过。
8. 记录**每条** `existing/implemented/blocked` 的最终状态，列出实际新增数量、已有复用数量、无法完成数量、原因及对应测试。不能以“内置数据成功加载”代替“技能已做完”。
9. 提供给玩家可浏览的「文化技能图鉴」与对应中文／日文／英文说明，且新对阵结果可沿用现有 SNS 分享和比赛结算。
10. 修改前保留版本控制记录，提交清晰可审查的源码与测试。不要反复请用户确认「下一批」。
