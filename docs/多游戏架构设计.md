# Glyph Rumble 三游戏架构设计（擂台 / 足球 4v4 / 篮球 2v2）

> 设计理念：**一个字是一个角色，两个字是一对搭档，四个字是一支球队。**
> 本文回答三个问题：三个游戏怎么分文件夹、怎么共用同一套文字角色、上线后怎么在页面顶部切换。

---

## 1. 目录结构

```
GameDevelopmentRandom/
├─ shared/            所有游戏共用：文字角色系统 + 3D 字形 + 分享 + 语言 + 游戏切换栏
│  ├─ src/core/       输入解析、字形分析、属性/性格/元素、必杀技表（唯一的角色数据库）
│  ├─ src/render/     字形渲染、3D 建模、角色缓存、粒子特效
│  ├─ src/share/      分享链接、SNS、系统分享、战报 PNG、分享面板、匿名统计
│  ├─ src/i18n/       语言状态（三个游戏共用一个 localStorage 键）+ 角色描述文案
│  ├─ src/ui/GameSwitcher.ts   顶部「擂台 / 足球 / 篮球」切换栏
│  ├─ docs/skills/    技能文档（从代码自动生成）
│  └─ docs/design/    你给的词汇设计稿（原样保存）
├─ arena/             字形乱斗 3D：擂台 1v1（现有游戏，已完成）
├─ soccer/            字形足球 4v4（已完成，见 soccer/README.md）
├─ basketball/        字形篮球 2v2（已完成，见 basketball/README.md）
├─ portal/            网站根目录的入口页（三个游戏的卡片）
├─ deploy/            部署说明 + 每局 OG 预览的边缘函数
├─ scripts/build-all.mjs   一次构建全部游戏 → dist/
└─ soundeffectRaw/    你放原始音效的地方（各游戏从这里挑文件放进自己的 public/audio/）
```

为什么多一个 `shared/`：设计稿要求「不要制作三套不同的文字数据库」「火 在三个模式里都是火属性」。
如果三个文件夹各复制一份角色代码，改一个字的技能就要改三处，迟早会对不上。
所以三个游戏文件夹只放**各自的玩法**（规则、AI、物理、场地、解说），角色本身只有一份，放在 `shared/`。

技术上用 npm workspaces：根目录 `npm install` 一次，三个游戏都能用 `@shared/...` 引用共用代码；Vite 打包时把用到的部分各自打进去，上线后三个游戏仍然是互相独立的静态网站。

## 2. 上线方式与顶部切换

```
https://你的域名/              入口页（三张卡片，未上线的游戏显示「即将推出」）
https://你的域名/arena/        擂台
https://你的域名/soccer/       足球
https://你的域名/basketball/   篮球
https://你的域名/s/<游戏>?…    （可选）每局 OG 预览的分享入口，见 deploy/README.md
```

- **切换栏**：每个游戏顶部都有同一个切换栏（`shared/src/ui/GameSwitcher.ts`）。上线后是同一网站下的相邻文件夹，链接用相对路径 `../soccer/`。开发时三个游戏各开一个端口：擂台 5173、足球 5174、篮球 5175，切换栏会自动指向对应端口。
- **语言**：三个游戏同源，语言选择存在同一个 `localStorage` 键里，切到别的游戏语言不变。
- **未完成的游戏**：`GAMES` 表里 `ready: false` 时显示为灰色「准备中」，不能点。做好一个就改成 `true`。
- **构建**：根目录 `npm run build` 依次构建存在的游戏，输出到 `dist/arena/`、`dist/soccer/`、`dist/basketball/`，并把 `portal/` 作为 `dist/index.html`。设置 `SITE_URL=https://你的域名/` 后，每个游戏的 OG 地址会自动变成绝对地址。

为什么不做成一个大 SPA 里的三个模式：三个游戏的场景、物理和资源差别很大（擂台的观众席、足球场、篮球场、音效、BGM），分开打包时玩家只下载自己玩的那个，首屏更快，一个游戏出问题也不影响另两个。共用代码通过 `shared/` 保证一致。

## 4. 组队：两种方式必须分清

```ts
type TeamInput =
  | { how: 'split'; word: string }          // 一键组队：「龙飞凤舞」→ 龙 / 飞 / 凤 / 舞
  | { how: 'free'; members: string[] };      // 自由组队：「妈妈」「爸爸」「宝宝」「奶奶」各是一名球员
```

- **一键组队**按 Unicode 字素簇拆分，必须正好 4 个（足球）或 2 个（篮球）字素，否则提示「请输入 4 个字，或改用自由组队」。`👨‍👩‍👧` 是 1 个字素，不会被拆成 3 个。
- **自由组队**的每个输入框就是一名球员，整词保留原技能：「妈妈」用妈妈的技能，不会变成两个「妈」。
- **英文单词不会自动拆**：`LOVE` 在一键组队里会被拒绝（不是 4 个可识别的单字角色时提示改用自由组队），只有用户主动选择才拆。
- 球队名：一键组队时就是原词「龙飞凤舞」；自由组队时用「妈妈·爸爸·宝宝·奶奶」，或玩家自己起的队名。
- 成语**不是第五名球员**，只是球队的组合信息，用来查连携表。

## 5. 体育技能：从现有必杀技映射，不重写

每个角色已有 `signature.kind`（38 类）和 `opts`。体育模式只加一张映射表：

| 现有机制（例） | 足球 | 篮球 |
|---|---|---|
| charge / fireCharge / rage / giant | PowerShot（强力射门，带冲撞） | 暴力灌篮 |
| whirlwind / sweep / magnet | CurveShot（弧线球）/ AreaControl | 转身突破 / 吸引防守 |
| kick / uppercut / mountain / giantFall | Knockback（铲球 / 撞飞） | 盖帽 / 抢篮板 |
| vanish / feint / ghost 标签 | Teleport（甩开盯防） | 换位 / 假动作 |
| shield / lazy / blame | Guard（守门 / 挡拆） | 防守站位 |
| freeze / glare / lecture / confuse | 控制：对手短暂停顿 | 抢断成功率提升 |
| drop / meteor / bribe / joke | 干扰：场上道具挡路 | 干扰投篮 |
| clones / swallow / random | Combo / Assist（分身传球、吞球再吐出） | 空中接力 |

- 「火」仍是火属性：擂台喷火冲撞 → 足球火焰射门（燃烧区域）→ 篮球火焰灌篮。
- 「404」原本是消失：足球里瞬移甩开盯防，篮球里换位，**不会无条件进球**。
- 所有体育技能都有发动条件、冷却和成功率，不是播一行字就让球进门。
- 属性映射独立平衡：重的字对抗强、加速慢；稳定的字控球和防守好；灵活的字转向快；细长的字接触范围稍大但有上限。碰撞体统一用**胶囊/圆柱代理**，半径有上下限，复杂汉字不会因为笔画多就变成一堵墙。

## 6. 连携（第二层能力）

和必杀技表一样做成数据表，每条有：组合词、模式（足球/篮球）、名称（三语）、**发动条件**、**冷却**、**实际效果参数**。

- 足球优先做视觉差异大的 4–6 条：龙飞凤舞（连续空中传球 + 弧线射门）、四面楚歌（四人包围持球者）、鸡飞狗跳（全场乱跑、球乱弹）、一鸣惊人（蓄力远射）、画蛇添足（射门后多踢一脚，可能踢偏）、大吉大利（一次幸运弹跳）。
- 篮球优先：冰火（冰造滑行空间，火灌篮）、真假（假投真投）、黑白（交叉换位）、兄弟（快速二传接空中接力）、摸鱼（倒地滑行后弹起投篮）。
- 不在表里的组合仍是正常球队，只用普通团队战术，**不自动给强效果**。

## 7. 球队分享链接

沿用现在擂台的链接格式（`mode` + `v` + 名单），多名球员用重复参数：

```
/soccer/?mode=soccer&v=1&how=split&an=龙飞凤舞&bn=风平浪静&a=龙&a=飞&a=凤&a=舞&b=风&b=平&b=浪&b=静
/basketball/?mode=basketball&v=1&how=free&a=爸爸&a=妈妈&b=404&b=ERROR
```

- 挑战链接：只有名单 → 朋友打开自动填好，用自己的队来挑战。
- 战报链接：再加 `seed` 和 `r`（比分、MVP、最精彩的真实连携/必杀），只展示真实结果，不重新模拟冒充。
- 人数随模式固定（足球 4、篮球 2），不会再被当成 3v3。

## 8. 足球 4v4 的玩法核心（soccer/，已实现）

- **模拟**：和擂台一样是确定性的固定步长模拟（同一种子可重放），渲染只读模拟状态。
- **球**：真实的抛物线 + 弹跳 + 滚动摩擦 + 旋转（弧线球），与球员、球门柱、横梁碰撞。进球 = 球整体越过门线且在门框内。
- **没有固定守门员**：每一刻按位置给 4 人分配角色——持球者、接应、前插、回防；球进入本方危险区时，离球门最近的回防队员临时成为守门员（可以扑救）。
- **AI**：效用评分（utility scoring），每 0.1 秒评估一次：带球 / 传球（看空位和拦截风险）/ 射门（看角度和距离）/ 抢断 / 铲球 / 使用技能 / 发动连携。不需要大语言模型。
- **比赛**：约 120 秒，进球后中圈开球；平局进入 20 秒「金球」加时，再平则平局。
- **表现**：参考《热血足球》的夸张——必杀射门带特写与冲击波、铲球把人撞飞、进球庆祝；但每一球都有真实判定。

## 9. 篮球 2v2 的玩法核心（basketball/）

- **场地**：缩小的双篮筐球场，双方各攻一个篮筐。
- **投篮**：按目标计算出手速度，再按技能、距离和防守干扰加上误差；球真实飞行，与篮筐/篮板碰撞，进筐判定是球心从上往下穿过篮圈平面。距离线外 3 分，其余 2 分。
- **动作**：运球突破、传球、假动作、投篮、灌篮（角色与球一起跃向篮筐）、空中接力、抢断、盖帽、篮板、回防。没有手脚，全部用字形本体的弹跳、旋转、倾斜、拉伸表现。
- **两人配合**：持球者吸引防守时，搭档自动切入空位；有连携的搭档优先尝试连携，但不保证成功。
- **比赛**：约 90 秒，时间到按分数决胜；同分进入 15 秒加时，再同分则平局。

## 10. 性能

- 8 / 4 名球员共用模板缓存，同一个字只建一次模型；观众沿用擂台的 InstancedMesh 做法。
- AI 每 0.1 秒决策一次，物理每帧 60 Hz；避免每帧分配临时对象。
- 只开一盏投影光，低画质下关阴影、降分辨率；粒子沿用 shared 的批量粒子（一种粒子一次绘制）。
- 所有特效 Shader 在加载时预编译，第一次必杀射门不卡顿。

## 11. 足球实现后的调整（与上文的差异）

- 平局：金球加时 20 秒，再平则平局（和第 8 节一致）。
- 守门：「谁离本方球门最近谁守门」已实现；`无法无天` 期间没人愿意守门。
- 平衡：体育属性（速度、控球、防守）刻意压窄，否则四人对四人时速度差会决定一切；铁壁类技能也削弱过。16 支测试队的胜率 18%–67%（擂台是 23%–77%）。
- 连携的强度：每个连携给本队带来约 0～+9 个百分点的胜率，不会「一发动就进球」。
- 篮球要用的 `BASKETBALL_COMBOS` 已在 shared 里登记，技能映射和组队、链接可以直接复用。

## 12. 开发顺序（建议）

1. ✅ **第 0 步：共用体育层（shared/src/sports/）**——组队解析、连携表、体育技能映射、球队链接格式与测试。
2. ✅ **足球 4v4（soccer/）**：从开球到结算完整可玩，测试见 soccer/tests/。
3. ✅ **篮球 2v2（basketball/）**：从跳球到结算完整可玩，91 组搭档技 + 16 组篮球对阵，测试见 basketball/tests/。
4. 每个游戏都要能从开球玩到结算，并通过设计稿第 21 节的测试清单；完成后把切换栏里的 `ready` 改成 `true`，入口页自动点亮。
5. 擂台和足球每次都跑全部测试，确保没有回归。
